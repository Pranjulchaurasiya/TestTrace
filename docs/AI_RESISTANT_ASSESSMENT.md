# TestTrace AI-Resistant Assessment Framework

This document outlines the pedagogical and technical mechanisms employed by **TestTrace** to evaluate actual student understanding in an era of ubiquitous Large Language Models (LLMs).

---

## 1. Why "AI Detectors" Fail

Conventional approaches to preventing AI cheating attempt to classify whether a block of submitted code was generated by an LLM (using perplexity or token probability classifiers). In practice, this strategy suffers from severe flaws:
1. **High False Positive Rates:** Idiomatic, clean, standard programming patterns (e.g., standard binary search or loop patterns) frequently trigger AI detectors, penalizing diligent students.
2. **Trivial Evasion:** Subtle variable renames, manual comment additions, or minor formatting changes completely disrupt statistical classifiers.
3. **No Pedagogical Value:** Accusing a student of using AI based solely on a probabilistic classifier is legally and academically tenuous.

**The TestTrace Philosophy:**
> Do not attempt to detect whether code was authored by an LLM. Instead, design the assessment so that a student cannot successfully complete it without genuine comprehension of the solution.

---

## 2. The 5-Layer AI-Resistant Framework

```
┌─────────────────────────────────────────────────────────────┐
│                 5-Layer Assessment Defense                  │
├─────────────────────────────────────────────────────────────┤
│ 1. Parameterized Seeds & Dynamic Problem Variants           │
│ 2. Deliberate Debugging & Flawed Implementation Tasks       │
│ 3. Execution Tracing & State-Change Prediction              │
│ 4. Post-Submission Explanation Step (The Mini-Viva)         │
│ 5. Modification Challenges (Live Code Mutation)             │
└─────────────────────────────────────────────────────────────┘
```

### Layer 1: Parameterized Problem Seeds
Instead of presenting identical numeric values or string literals to every examinee, question prompts are parameterized using a deterministic hash of the student's ID and the exam attempt seed:
$$\text{Variant Seed} = \text{SHA256}(\text{student\_id} + \text{exam\_id} + \text{salt})$$

* **Example:**
  - *Student A:* "Find all pairs in array `[14, 28, 9, 31, 4]` that sum to `35`."
  - *Student B:* "Find all pairs in array `[22, 17, 8, 39, 13]` that sum to `30`."
* *Result:* Directly copying prompts into an external device without adapting constants leads to immediate test case failures.

---

### Layer 2: Deliberate Debugging Tasks
Rather than asking students to generate generic boilerplate from scratch, provide partially implemented programs containing subtle conceptual errors (e.g., off-by-one errors, mutable default arguments, reference vs. value mutations):

```python
def find_median(numbers):
    numbers.sort()
    mid = len(numbers) // 2
    if len(numbers) % 2 == 0:
        return numbers[mid]  # Bug: Off-by-one average calculation missing
    return numbers[mid]
```
The student is required to identify the exact line of failure, explain the root cause, and rectify it. This tests code reading and debugging acumen rather than memorization.

---

### Layer 3: Execution Tracing & State-Change Prediction
Ask the student to predict intermediate memory states after specific loop iterations:
* "After 3 iterations of the while loop on line 6 with input `x = 12`, what are the exact contents of stack `s`?"
A student who understands the algorithm can answer in 10 seconds; someone consulting an external chatbot must feed the entire trace context and parse lengthy explanations.

---

### Layer 4: Post-Submission Explanation Step (The Mini-Viva)

This is the primary defense mechanism against copied or LLM-generated code.

1. **Trigger Condition:** The instant a student clicks **"Submit Code"**, their solution is locked.
2. **Immediate Follow-up:** The student is immediately presented with 2 short, rapid-fire explanation prompts derived from their own submission.
3. **Strict Rapid Timer:** Each prompt has an independent 30 to 45-second countdown.
4. **Targeted Questions:**
   - *"Explain why you chose a hash map on line 4 instead of a sorted list."*
   - *"What would happen to your output on line 9 if negative values are introduced?"*
   - *"What is the exact asymptotic space complexity of your auxiliary recursion stack?"*

**Pedagogical Outcome:**
- A student who authored the solution knows their code structure intimately and can answer immediately.
- A student who pasted code from a secondary device or hidden clipboard must first read and comprehend unfamiliar code before answering, typically causing time expiration or superficial explanations.

---

### Layer 5: Live Code Mutation (Modification Prompts)
Once the base code passes, prompt the student to make an immediate, small modification within 60 seconds:
- *"Modify your function so it returns the indices rather than the values."*
- *"Update line 12 so that ties are broken in alphabetical order."*

---

## 3. Examiner Integrity Review Matrix

All signals are combined into an **Integrity Risk Index**:

$$\text{Risk Score} = \sum (\text{Browser Signals}) + \sum (\text{Computer Vision Signals}) + \text{Viva Delay Penalty}$$

| Indicator | Nominal Behavior | Cheating Suspect Profile |
| :--- | :--- | :--- |
| **Typing Velocity** | Gradual keystroke accumulation with edits and backspaces | Sudden large paste burst ($> 150$ characters in $< 1$s) followed by immediate run |
| **Viva Explanation** | Response submitted in 15–25 seconds with clear personal phrasing | Response timed out ($> 45$s) or completely disconnected from submitted syntax |
| **Gaze / Head Pose** | Continuous focus on screen and editor | Multiple repeated head pitch/yaw deviations ($> 25^\circ$) immediately preceding code runs |
| **Browser Focus** | Fullscreen maintained throughout session | Repeated tab blur / hidden state changes |

These signals are provided to the teacher on the **Attempt Timeline & Audit Screen**, ensuring that final academic decisions remain human-reviewed and evidence-grounded.
